### 참가 취소 기능 개발 중 겪은 문제들

**1. 엉뚱한 PK로 조회하는 실수**
`findByIdForUpdate(meetingPostId)`처럼 파라미터 이름과 실제 넘긴 값의
의미가 다른 코드를 작성했다. Long 타입끼리라 컴파일러가 잡지 못했고,
동시성 테스트를 짜는 과정에서 발견했다. 타입 시스템이 못 잡는 실수는
테스트로 검증해야 한다는 걸 다시 확인.

**2. JPQL에서 연관 엔티티와 ID를 직접 비교**
`WHERE p.member = :memberId`처럼 엔티티 필드와 Long 값을 비교하는
JPQL을 작성해 `InvalidDataAccessApiUsageException`이 발생했다.
`p.member.id = :memberId`로 명시적으로 id 필드까지 접근해야 했다.

**3. 테스트 setUp()의 중복 저장으로 데이터 정합성 붕괴**
동일 엔티티를 반복문 안에서 두 번 저장하는 실수로 인해 테스트 데이터
개수가 의도한 것의 2배가 되었고, 이로 인해 무관해 보이는 다른
테스트까지 함께 실패했다. 동시성 테스트처럼 정확한 데이터 상태를
전제로 하는 테스트는 setUp() 자체의 정합성을 먼저 의심해야 한다는
교훈을 얻음.

**4. 프론트 로컬 state 필터링이 항상 무효였던 문제**
취소 API는 성공하는데 마이페이지 카드가 새로고침 전까지 사라지지
않는 문제가 있었다. 원인은 백엔드 조회 쿼리(findAllAppliedByMemberId)가
Participation 상태와 무관하게 전체 이력을 반환하고 있었기 때문.
즉시 제거(filter) 대신 상태만 갱신(map)하는 방식으로 프론트 로직을
바꾸고, CANCELLED 상태에 대한 뱃지/버튼 조건을 추가해 해결했다.
"안 사라진다"는 현상만 보고 프론트 코드부터 의심했지만, 실제 원인은
백엔드 쿼리의 필터 부재였다 — 증상의 위치와 원인의 위치가 다를 수
있다는 걸 다시 확인.
